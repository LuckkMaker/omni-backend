# USB 原始请求（Bus Hound 式）可行性与路线

> 状态：论证稿；**不进入本轮实现**（M3 已用 WinUSB/HID/CDC 三条通道落地，原始访问仍只做论证）  
> 结论先行：技术可行，但本质是"写一个内核驱动"或"带一个第三方内核驱动"，
> 属于产品级投入，不是一个 CLI 功能。

## 1. Bus Hound 是怎么做到的

Bus Hound 安装时会写入一个**内核态过滤驱动**，挂在 USB 设备栈上；它的 GUI 通过
这个驱动下发的设备接口提交 URB。所以它能"看见并发送任意设备的 SETUP"，
不是绕过了驱动，而是**它自己就是那一层驱动**。

同类证明：

- USBPcap：内核过滤驱动，只读（能看不能发）；
- UsbDk（Red Hat，开源）：总线过滤驱动 + 用户态 helper，QEMU/SPICE 用它做任意
  USB 设备重定向，能发控制/批量/中断；
- libusbK / libusb-win32：功能驱动替换（Zadig 安装），能发但不"透明"。

三者都要求**装驱动 + 管理员 + 通常重启**，这是 Windows 的硬约束，不是实现选择。

## 2. 三条路线

| 维度 | A. 集成 UsbDk | B. 自研驱动 | C. WinUSB（现状） |
| --- | --- | --- | --- |
| 覆盖设备 | 任意（接管期间） | 任意（接管期间） | 仅绑定 WinUSB 的接口 |
| 开发量 | 2–4 周集成 + 2 周验证 | 控制传输 2–3 个月；批量/等时 4–6 个月（见 [驱动设计](usb-filter-driver-design.md)） | 已具备 |
| 驱动签名 | 用 UsbDk 已发布版本（需核实 Win11/Secure Boot） | EV 证书 + attestation/WHQL，年费与流程 | 不需要 |
| 设备影响 | 接管时设备从系统消失 | 同左 | 无 |
| 分发 | 需安装驱动（管理员 + 重启） | 同左 + 安装器/卸载器 | 无 |
| 维护风险 | 上游项目基本停更 | 每代 Windows 自担 | 跟随微软 |
| 许可证 | 需逐条核对（驱动二进制再分发） | 自有 | 自有 |

## 3. 建议：先花 2 周验证 UsbDk（路线 A）

若"任意设备发请求"是刚性需求，先做 spike，而不是直接立项自研。验证清单：

1. **安装与加载**：Win10 22H2 / Win11 24H2、Secure Boot 开启时能否安装并加载；
2. **能力**：控制传输、批量/中断 pipe、等时传输是否可用；最大包长/超时行为；
3. **恢复**：接管期间设备对系统不可见；主动释放、进程崩溃、蓝屏后设备是否恢复；
4. **共存**：接管同时 USBPcap 是否仍能抓包（这是"发请求立刻看到 URB"的前提）；
5. **许可**：UsbDk LICENSE 是否允许随 OMNI 分发其签名驱动；安装器条款；
6. **API**：`UsbDkHelper.dll` 的调用面是否稳定（控制/批量/中断/取消/超时）。

通过标准：上面 6 项全绿，且设备恢复无残留。任一项不通过就停下重新评估。

## 4. 若自研（路线 B）的范围

详见 [自研 KMDF 驱动设计](usb-filter-driver-design.md)。核心结论：

- **只发 SETUP**：上层过滤驱动 + 直接向 PDO 提交控制 URB，不替换原驱动，
  但接管期间与功能驱动并发，需显式 claim；
- **要发批量/中断**：必须拿到 `USBD_SelectConfiguration` 的 pipe handle，
  只能做**通用功能驱动**（自研 WinUSB 克隆），设备在接管期间从系统消失；
- **等时**：功能驱动之上再加等时调度，成本最高。

驱动本身不是最难的，难的是签名（EV + attestation/WHQL）、安装卸载、
PnP/电源/取消/热插拔的完备性，以及蓝屏责任。

## 5. 架构衔接（无论 A/B）

`usb_host` 从一开始就按 **provider 抽象**设计：

```
usb_host.py
├── provider="winusb"     # 默认：绑定设备，控制/批量/中断
├── provider="hid"        # 报告级
├── provider="cdc"        # COM 复用
└── provider="raw"        # 将来：UsbDk 或自研驱动（opt-in）
```

CLI：`omni usb open --provider raw`（默认 `winusb`）；`doctor` 检查驱动是否安装。
安全策略：`raw` 必须显式选择设备 + 二次确认，退出时强制释放。

## 6. 结论

- **已落地**：M3 按 WinUSB/HID/CDC 三条通道实现（覆盖自家固件，零驱动依赖）；
- **仍未做**：任意设备（被 usbstor/厂商驱动占用）的原始访问，需要 UsbDk 或自研驱动；
- **决策点**：若业务确实需要任意设备，先做 2 周 UsbDk 验证（第 3 节清单）；
  通过则做 opt-in 的 `provider=raw`（约 1 个月），不通过且需求刚性 → 单独立项自研，
  不塞进 OMNI 的 USB 迭代。
